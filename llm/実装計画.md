# Pegmatite Vault 実装計画

## 1. 目的

既存の画面構成案とDB設計を基に、鉱物標本を登録・検索・閲覧・管理できる個人用Webアプリケーションを段階的に実装する。

最初に標本管理の主要動線を完成させ、その後に鉱物図鑑、採集地、マスタ管理、バックアップ機能へ広げる。

## 2. 確定した実装方針

| 項目 | 採用技術・方針 |
| --- | --- |
| フロントエンド | React（JavaScript）＋ Vite |
| バックエンド | FastAPI |
| DB | PostgreSQL |
| ORM・マイグレーション | SQLAlchemy 2.x ＋ Alembic |
| APIスキーマ | Pydantic |
| 画像保存 | ユーザーが指定できる、バックエンド管理のローカルディレクトリ |
| 認証 | なし |
| API形式 | REST API、JSON（画像アップロードのみ multipart/form-data） |
| 開発環境 | Docker ComposeでPostgreSQLを起動し、フロントエンドとバックエンドはローカル実行 |

認証を実装しないため、初期版は個人PCまたは信頼できるLAN内での利用を前提とする。インターネットへ直接公開しない。

## 3. 既存資料の確認結果

### 3.1 利用する資料

- `docs/db/`: テーブル定義、ER図、外部キー制約
- `docs/frontend/画面遷移.md`: 画面間の主要な遷移
- `llm/ドキュメント構成案.md`: 画面、ルーティング、ワイヤーフレーム、実装優先順位
- `llm/画面構成.md`: 共通レイアウト案

### 3.2 整合している方針

- HOME、VAULT、LIBRARY、ADMIN、SETTINGを主要領域とする。
- 標本を中心に、鉱物種、採集地、入手経路、画像を関連付ける。

- マスタデータの削除時は、外部キー制約に従って使用中レコードの削除を拒否する。

### 3.3 実装前に確定・補完する事項

以下はコード着手時に、マイグレーションとAPI仕様へ明文化する。

1. `specimens.specimen_no` の採番と一意性
   - 採集地ごとの通し番号として扱うが、`locality_id` と組み合わせた一意制約は設けない。
   - 値を指定せずに新規登録する場合、APIが同じ採集地に属する標本の最大番号へ1を加えた値を割り当てる。
   - `locality_id` がNULLの場合は、採集地未設定の標本の最大番号へ1を加える。
   - 利用者が番号を明示した場合は、その値を使用する。重複も許容する。
   - DB制約を緩く保つため、この採番は厳密な連番や一意性を保証するものではない。
   - 同時登録時に同じ番号が割り当てられる可能性は許容し、将来厳密な管理番号が必要になった場合は、別途 `catalog_number` の追加を検討する。
2. NULL許可
   - `locality_id`、`acquisition_method_id`、`mineral_class_id` は未確定データを登録できるようNULL許可とする。
3. 日時
   - `created_at` と `updated_at` はタイムゾーン付き日時としてDB側・アプリ側ともUTCで保存する。
   - UIでは利用環境のローカル時刻で表示する。
   - タイムゾーンはブラウザから自動取得し、利用者による設定項目は設けない。
4. 画像
   - `images` は1つの画像資産につき1レコードとし、オリジナル、表示用、サムネイルのパスを個別に保持しない。
   - 利用者が選択した元画像は移動・変更せず、アプリ専用の画像保存先へ複製する。
   - 画像保存先は設定可能にし、現在の保存先をSETTING画面で確認できるようにする。
   - 初期起動時は環境変数 `IMAGE_STORAGE_ROOT` で保存先を指定する。実行中の保存先変更はPhase 4で実装する。
   - 保存パスは画像レコードのUUIDから規則的に導出する。UUID化により、同名ファイルの上書き、OSで扱えない文字、パストラバーサルを防ぐ。
   - 既存の `images` 設計を補完し、`original_filename`、`original_extension`、`media_type`、`file_size`、`status`、`archived_at`、`created_at` を追加する。`file_path` は使用しない。
   - オリジナル複製は恒久データとして扱う。表示用画像とサムネイルは再生成可能な派生データとして扱う。
   - JPEG、PNG、WebPを初期対応形式とし、サイズ上限を設定する。
5. ページング
   - 一覧APIは `page` と `page_size` を使用し、総件数を返す。
6. 削除
   - 標本削除時は関連する画像レコードとファイルを削除せず、`status = archived` と `archived_at` を設定する。
   - 論理アーカイブではファイルを移動しないため、DBとファイルのパス対応を維持できる。
   - アーカイブ画像は通常の一覧や画像配信対象から除外し、Phase 4の復元操作で標本へ再関連付けできるようにする。
   - 完全削除は通常の標本削除と分け、SETTING画面から明示的に実行する。完全削除時のみDBレコードと画像ファイルを削除する。

## 5. アーキテクチャ

```text
React
  ↓ HTTP / JSON
FastAPI routes
  ↓
Service（業務処理・画像処理）
  ↓
Repository / SQLAlchemy
  ↓
PostgreSQL

画像アップロード
  ↓
FastAPI
  ├── メタデータ → PostgreSQL
  └── 複製・派生画像 → <IMAGE_STORAGE_ROOT>/images/<image UUID>/
```

フロントエンドからDBや画像保存先を直接操作しない。入力検証、関連レコードの存在確認、削除制約、画像ファイル名生成はバックエンドへ集約する。

## 6. API実装範囲

### 6.1 共通

- `GET /api/health`: アプリとDBの稼働確認
- エラー形式を統一する。
- 一覧レスポンスに `items`、`page`、`page_size`、`total` を含める。
- 存在しないIDは404、入力不正は422、削除制約違反は409を返す。

### 6.2 標本

- `GET /api/specimens`
- `POST /api/specimens`
- `GET /api/specimens/{id}`
- `PATCH /api/specimens/{id}`
- `DELETE /api/specimens/{id}`
- キーワード、鉱物種、採集地、お気に入りによる検索・絞り込み
- 作成日時、標本番号、標本名による並び替え

### 6.3 画像

- `POST /api/specimens/{id}/images`
- `PATCH /api/images/{id}`
- `DELETE /api/images/{id}`
- `PATCH /api/specimens/{id}/images/order`
- `GET /api/images/{id}/content?variant=original|display|thumbnail` で画像配信
- アップロード時にオリジナルを複製し、表示用画像とサムネイルを生成
- 標本削除時に画像レコードを論理アーカイブ

### 6.4 鉱物・採集地

- `GET /api/minerals`
- `GET /api/minerals/{id}`
- `GET /api/localities`
- `GET /api/localities/{id}`
- 詳細APIでは関連標本をページングして取得できるようにする。

### 6.5 管理対象

- `minerals`
- `mineral-classes`
- `localities`
- `acquisition-methods`

各リソースに一覧、作成、取得、更新、削除APIを用意する。標本から参照されているマスタは削除を拒否する。

### 6.6 設定・データ管理

- CSVエクスポート
- CSVインポート
- DBバックアップ手順の提供
- 画像を含むバックアップ／リストアは最終段階で実装する。
- 画像保存先の表示・変更
- アーカイブ画像の一覧、復元、完全削除

## 8. 段階的な実装計画

### Phase 0: 基盤と仕様固定

1. README、`.gitignore`、`.env.example` を整備する。
2. ViteでReactプロジェクトを作成する。
3. FastAPIプロジェクトとPython依存管理を構成する。
4. Docker ComposeでPostgreSQLを起動できるようにする。
5. CORS、環境変数、ログ、例外レスポンスを設定する。
6. SQLAlchemyモデルと初回Alembicマイグレーションを作成する。
7. 画像保存先の設定、書き込み可否チェック、管理フォルダの初期化を実装する。
8. マスタの初期データ投入方法を作成する。
9. ヘルスチェックと最小の結合テストを通す。

完了条件:

- フロントエンド、API、DBをローカルで起動できる。
- Alembicで空DBを最新状態へ構築できる。
- `GET /api/health` がDB接続状態を含めて成功する。
- 設定した画像保存先の読み書きを起動時に検証できる。

### Phase 1: 標本管理の主要動線

1. 共通レイアウトとReact Routerを実装する。
2. 標本APIのCRUDを実装する。
3. 鉱物、採集地、入手経路の選択肢APIを実装する。
4. VAULTの標本一覧を実装する。
5. 標本詳細を実装する。
6. 標本登録・編集フォームを実装する。
7. 標本削除と確認ダイアログを実装する。
8. 複数画像の複製アップロード、リサイズ、サムネイル、表示、並び替え、アーカイブを実装する。
9. HOMEのお気に入り・最近追加した標本を実装する。

完了条件:

- 画面から標本と関連鉱物を登録、閲覧、編集、削除できる。
- 画像を複数登録し、代表画像として先頭画像のサムネイルを一覧表示できる。
- ブラウザ更新後も登録内容と画像が保持される。
- 標本を削除しても画像一式はアーカイブに残る。

### Phase 2: 検索と図鑑

1. VAULTのキーワード検索、絞り込み、並び替え、ページングを実装する。
2. グリッド表示とリスト表示を実装する。
3. LIBRARYの鉱物一覧・分類表示を実装する。
4. 鉱物詳細と関連標本一覧を実装する。
5. 採集地詳細と関連標本一覧を実装する。
6. URLクエリに検索条件を保持し、戻る操作で状態を復元する。

完了条件:

- 主要な検索条件を組み合わせても正しい結果と件数が返る。
- 鉱物・採集地から関連標本へ遷移できる。

### Phase 3: 管理機能

1. ADMINトップを実装する。
2. 鉱物、鉱物分類、採集地、入手経路の一覧・登録・編集を実装する。
3. 使用中マスタの削除拒否と、理由を示すUIを実装する。
4. 管理画面の共通テーブル・フォーム部品を整理する。

完了条件:

- 全マスタを画面から管理できる。
- 外部キー制約違反が500エラーにならず、利用者に理解できる形で表示される。

### Phase 4: 設定・データ保全

1. SETTING画面を実装する。
2. CSVエクスポートを実装する。
3. 検証結果を事前表示するCSVインポートを実装する。
4. PostgreSQLと画像ディレクトリを一組としてバックアップする手順を整備する。
5. リストア手順と検証方法を整備する。
6. 画像保存先の表示と変更を実装する。
7. 保存先変更時は既存ファイルの移行前検証、コピー、整合性確認を行い、成功後に設定を切り替える。
8. アーカイブ画像の一覧、復元、完全削除を実装する。
9. ストレージ使用量とアプリバージョンを表示する。

完了条件:

- 新しい環境へDBと画像を復元できる。
- 不正なCSVで既存データが部分的に破損しない。
- 保存先の変更に失敗しても、旧保存先と設定が維持される。
- アーカイブ画像を選択した標本へ復元できる。

### Phase 5: 品質改善とリリース準備

1. アクセシビリティ、キーボード操作、レスポンシブ表示を確認する。
2. 大量データ時のクエリ数、インデックス、画像表示性能を確認する。
3. APIと画面の主要シナリオを自動テストする。
4. セキュリティヘッダー、アップロード検証、パストラバーサル対策を確認する。
5. セットアップ、更新、バックアップ、障害復旧手順をREADMEへ記載する。

完了条件:

- 新規環境でREADMEだけを参照して起動できる。
- 主要なCRUD、検索、画像、バックアップの検証が成功する。

## 9. テスト方針

### バックエンド

- pytestでサービス、API、DB制約をテストする。
- テスト用PostgreSQLを使用し、本番と異なるSQLiteへの置き換えは行わない。
- 主要対象:
  - 標本CRUD
  - 複数鉱物との関連付け
  - 検索、並び替え、ページング
  - 外部キー制約
  - APIによる標本番号の自動採番と手動指定
  - 画像形式、サイズ、複製、リサイズ、アーカイブ
  - DB失敗時のファイル整合性とアーカイブからの復旧

### フロントエンド

- VitestとReact Testing Libraryでフォーム、一覧、エラー状態をテストする。
- Playwrightで主要動線をE2Eテストする。
- 主要シナリオ:
  - 標本を登録して詳細を確認する。
  - 標本を編集して画像を追加する。
  - 条件検索して対象標本を開く。
  - 標本を削除する。
  - 使用中マスタの削除が拒否される。

## 10. 実装上の注意

- フロントエンドのJavaScriptにはESLintとPrettierを導入し、APIレスポンスの形を一貫させる。
- Reactコンポーネントから直接 `fetch` を散在させず、`src/api/` にAPIクライアントを集約する。
- FastAPIのルートへDB処理を詰め込まず、サービスとリポジトリへ分離する。
- 一覧取得時のN+1クエリを避け、代表画像や関連名を効率よく取得する。
- 検索対象列と外部キーには、利用状況に応じてインデックスを追加する。
- 画像のContent-Typeだけを信用せず、実データも検査する。
- 画像保存先は起動時と変更時に、存在、書き込み権限、空き容量を検査する。
- 保存先の変更で既存画像を移行するときは、先にコピーとハッシュ検証を完了し、旧ファイルの削除は自動では行わない。
- `.env` に秘密情報や環境固有値を保存し、Gitへコミットしない。
- 認証を追加する場合は、管理APIを含む全更新操作の認可設計を別途行う。

## 11. 最初の実装単位

最初の開発単位はPhase 0とし、以下を一つの到達点とする。

1. PostgreSQLを起動する。
2. Alembicで全テーブルを作成する。
3. FastAPIからDBへ接続する。
4. ReactからヘルスチェックAPIを呼び出す。
5. 共通レイアウトと空の主要ルートを表示する。
6. バックエンドとフロントエンドのテストを各1件以上実行する。

この基盤が安定してから、Phase 1の標本CRUDを縦方向に一機能ずつ完成させる。
