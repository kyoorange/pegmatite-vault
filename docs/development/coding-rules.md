# コーディング規約

## 共通

- コード、ファイル名、API、DBの識別子は英語を使用する。
- ユーザー向け文言とドキュメントは日本語を基本とする。
- 1つの関数・コンポーネントに複数の責務を持たせない。
- 仕様変更を伴う実装では、先に `docs/` を更新する。
- コメントは処理内容ではなく、判断理由や制約を説明する。
- 秘密情報、実画像、DBデータをGitへ追加しない。

## JavaScript・React

- React関数コンポーネントとhooksを使用する。
- JSXファイルは `.jsx`、一般JavaScriptは `.js` とする。
- コンポーネントは `PascalCase`、関数・変数は `camelCase`、定数は `UPPER_SNAKE_CASE`。
- ページはルーティングと機能の組み立てに留める。
- API通信は `src/api/` に集約し、成功・エラー形式を統一する。
- サーバーデータと一時的なUI状態を区別する。
- `useEffect` で派生状態を同期せず、可能な限りレンダー時に導出する。
- フォームは送信中の二重送信を防ぎ、APIの項目エラーを入力欄付近に表示する。
- リスト要素のkeyに配列indexを使わず、リソースIDを使う。
- ESLintとPrettierを必須とする。

## Python・FastAPI

- Pythonの公開関数、メソッド、属性に型注釈を付ける。
- RuffでLintとフォーマットを行う。
- FastAPIルートはHTTP変換に限定し、業務処理をserviceへ置く。
- SQLAlchemy 2.xの記法を使用する。
- PydanticモデルをDBモデルとして流用しない。
- DBセッションとトランザクションの境界をserviceで明示する。
- 広範な `except Exception` で握りつぶさず、既知の例外を共通APIエラーへ変換する。
- ファイルとDBを同時操作する処理は、補償処理と構造化ログを用意する。
- ログへDBパスワード、画像内容、不要な個人情報を出力しない。

## API

- [OpenAPI仕様](../api/openapi.yaml)を契約の正本とする。
- JSONは `snake_case`、URLの複合語はkebab-caseとする。
- `GET` は状態を変更しない。
- 作成は `POST`、全置換は `PUT`、部分更新は `PATCH`、削除は `DELETE`。
- 作成は201、削除成功は本文なしの204を返す。
- 一覧は `items`、`page`、`page_size`、`total` を返す。
- エラーは `error.code`、`error.message`、必要に応じて `error.details` を返す。
- 画像の物理パスをレスポンスへ含めない。

## DB

- テーブル・カラムは `snake_case`、複数形テーブル名を使用する。
- UUIDはアプリ側またはDB側のどちらで生成するかをモデル全体で統一する。
- 日時は `timestamptz` でUTC保存する。
- 外部キー列へ必要なインデックスを設定する。
- ORMのcascadeとDBの `ON DELETE` を混同せず、両方をレビューする。
- 一覧取得ではN+1クエリをテストで検出する。

## テスト

- バックエンドはpytest、フロントエンドはVitestとReact Testing Library、主要動線はPlaywrightを使用する。
- 不具合修正では、可能な限り先に再現テストを追加する。
- 正常系だけでなく、404、409、422、画像形式・サイズ超過を確認する。
- DBテストはPostgreSQLを使用する。
- テスト名は期待する振る舞いが分かる名称にする。

## Git

- 1コミットは1つの論理的変更にする。
- 生成物、`.env`、画像、DBボリュームをコミットしない。
- マイグレーションと対応するモデル変更は同じ変更単位に含める。
- 無関係な整形変更を機能変更へ混在させない。
